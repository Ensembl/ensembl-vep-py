    Edited boundaries: rebuilding the CDS around a variant¶

    How TranscriptVariationAllele._full_cds_alleles decides where the coding sequence starts and ends once a variant has been applied — and why one four-line function handles the start boundary, the end boundary, insertions and deletions without a single special case.

    Companion to Consequence annotators; the facts that consume this are cds_start_lost, cds_stop_lost, cds_start_retained and cds_stop_retained in annotators/consequence/facts/sequence.py.

    The problem¶

    The reference CDS is easy: spliced_seq[cdna0 : cdna0 + cds_length], where cdna0 is the CDS start as a 0-based offset into the spliced transcript. The alternate is not, because applying an edit moves the ground under both of those offsets.

    The edit is modelled uniformly — replace the half-open offset range [edit_start, edit_end) with the strand-corrected alternate allele — and applied to spliced_seq, the whole 5'UTR + CDS + 3'UTR in transcript sense. delta is the net length change. Introns never appear, because transcript_mapper is block-overlap based over the real exon list, so intronic bases map to no offset at all: splicing is always assumed to proceed normally.

    Naively reusing cdna0 and cdna0 + cds_length against the edited sequence is wrong in two opposite directions:

    • A deletion upstream of the CDS slides the whole CDS left. Read at the old cdna0 and you start several bases into the coding sequence.
    • A deletion that destroys the start codon has no CDS start to speak of any more. Fall back to the old offset and you silently anchor into leftover 5'UTR, inventing a start that was deleted.

    Both boundaries need the same treatment, so both go through one function.

    The function¶

    def _edited_boundary(boundary0: int, edit_start: int, edit_end: int, delta: int) -> int:
    if boundary0 < edit_start:      # edit lies AFTER the boundary
        return boundary0
    if boundary0 >= edit_end:       # edit lies BEFORE the boundary
        return boundary0 + delta
    return edit_start               # edit STRADDLES the boundary

    Called twice, and the result used as a plain slice:

    anchor    = _edited_boundary(cdna0,    edit_start, edit_end, delta)
end_bound = _edited_boundary(cds_end0, edit_start, edit_end, delta)
alternate_cds = _nucleotide_sequence_up_to_stop(alternate_spliced_seq[anchor:end_bound])

    The three cases¶

    A miniature transcript throughout: 4 bases of 5'UTR, a 9-base CDS, 4 bases of 3'UTR. cdna0 = 4; cds_end0 = 13 (exclusive, so it points at the first 3'UTR base).

      offset    01234567890123456
  spliced   uuuuATGGGGTAAnnnn
                ▲        ▲
              cdna0=4  cds_end0=13

    Case 1 — edit lies after the boundary → unchanged¶

    Nothing upstream of the boundary moved, so its offset is still correct.

      spliced   uuuuATGGGGTAAnnnn        delete offsets 7-9 ("GGG")
                ▲  ───               edit = [7,10)   delta = -3
              cdna0=4

  edited    uuuuATGTAAnnnn
                ▲                    anchor = 4  (unchanged)

    Case 2 — edit lies before the boundary → slides by delta¶

    The boundary still points at the same base; only its number changed. This is the case that looks alarming and is not: the anchor moves precisely because the sequence moved with it.

      spliced   uuuuATGGGGTAAnnnn        delete offsets 1-2 ("uu")
             ── ▲                    edit = [1,3)    delta = -2
                cdna0=4

  edited    uuATGGGGTAAnnnn
              ▲                      anchor = 2  ( = 4 + (-2) )

    Case 3 — edit straddles the boundary → collapses to edit_start¶

    The boundary no longer exists in the edited sequence — the bases that defined it are gone. The only defensible answer is the edit itself.

      spliced   uuuuATGGGGTAAnnnn        delete offsets 3-5 ("uAT")
               ───                   edit = [3,6)    delta = -3
                ▲                    cdna0=4 falls inside the edit

  edited    uuuGGGGTAAnnnn
               ▲                     anchor = 3  ( = edit_start )

    The same three cases apply unchanged to cds_end0; only the numbers differ.

      Case 1 (end)   delete offsets 14-15, in the 3'UTR   →  end_bound = 13  (unchanged)
  Case 2 (end)   delete offsets 7-9,  inside the CDS  →  end_bound = 10  ( = 13 - 3 )
  Case 3 (end)   delete offsets 11-14, stop + 1 UTR   →  end_bound = 11  ( = edit_start )

    Why one return value does opposite things at each end¶

    Case 3 returns edit_start for both boundaries, but anchor and end_bound are the two ends of a slice — inclusive lower, exclusive upper. The same number therefore has opposite meanings, which is exactly what is wanted at each end.

      STRADDLING THE START — replace offsets 3-5 with "XXXXX"

  edited    uuuXXXXXGGGGTAAnnnn
               ▲
             anchor = 3, an INCLUSIVE lower bound
             → alternate_cds = XXXXXGGGGTAA…    reads THROUGH the replacement


  STRADDLING THE END — replace offsets 11-14 with "XXXXX"

  edited    uuuuATGGGGTXXXXXnn
                       ▲
                   end_bound = 11, an EXCLUSIVE upper bound
             → alternate_cds = ATGGGGT          stops BEFORE the replacement

    Biologically that is the right pair of answers. An edit landing on the start codon replaces it, and whatever it puts there is what a ribosome would encounter first — so read it in. An edit landing on the stop codon destroys it, and nothing downstream can be trusted to be coding any more — so stop short. Neither case ever falls back into untouched UTR.

    Insertions can never straddle¶

    For a pure insertion edit_start == edit_end, which makes the straddle branch's range edit_start <= boundary0 < edit_end empty. Case 3 is unreachable for insertions — structurally, not by convention. An insertion sits between two bases, so it is always cleanly before or after any boundary, and only Cases 1 and 2 ever fire.

      spliced   uuuuATGGGGTAAnnnn        insert "AAA" at offset 7
                ▲  ∧                 edit = [7,7)    delta = +3
              cdna0=4                the insertion is a zero-width point, so
                                     cdna0 = 4 < 7 → Case 1, anchor unchanged

    Deletions and delins are the only edits that can destroy a boundary, which is why every straddle-case test in the suite is a deletion or a delins.

    The whole model in four lines¶

    Because both boundaries are resolved against the same edit, the width of the window falls out correctly on its own:

    Edit location anchor end_bound Net effect on the CDS
    Entirely 5' of the CDS +delta +delta window slides, width unchanged → identical CDS
    Entirely 3' of the CDS unchanged unchanged window untouched → identical CDS
    Inside the CDS unchanged +delta width changes by exactly delta
    Straddling a boundary = edit_start = edit_start that end re-anchors on the edit

    Verified against the real fixture (cdna0 = 9, cds_end0 = 45):

    Edit Range delta anchor end_bound alt == ref
    deletion in 5'UTR [2,6) −4 5 41 yes
    deletion straddling start [7,12) −5 7 40 no
    deletion inside CDS [14,18) −4 9 41 no
    deletion straddling end [42,46) −4 9 42 no
    deletion in 3'UTR [50,54) −4 9 45 yes
    insertion in 5'UTR [5,5) +3 12 48 yes
    insertion inside CDS [15,15) +3 9 48 no
    insertion in 3'UTR [50,50) +3 9 45 yes

    A variant that touches no exon at all (purely intronic, or entirely outside the transcript) never reaches this machinery — genomic_span_to_cds_offsets returns None and the property short-circuits to (reference_cds, reference_cds), the same no-op a UTR-only edit arrives at by actually applying the edit. None is returned only when the transcript has no CDS at all.

    Opt-in readthrough¶

    Everything above describes the default. A run may model what happens downstream of a destroyed stop codon by raising Readthrough (common/enums.py), which changes exactly one thing — the end_bound half of the table above:

    Readthrough end_bound Reads
    NONE (default) _edited_boundary(cds_end0, …) the CDS only
    UTR len(alternate_spliced_seq) on into the 3'UTR, still inside the transcript
    BEYOND_TRANSCRIPT as UTR, then bounded flanking sequence past the transcript, from slice.seq

    An IntEnum, so the levels are ordered rather than independent: BEYOND_TRANSCRIPT extends UTR, which makes "read past the transcript but not through the UTR" unrepresentable.

    It is not gated on "was the stop actually lost?", deliberately. An intact, in-frame stop terminates translation wherever the bound sits, so raising the level is provably a no-op for every variant that leaves the stop alone — the levels can only diverge when no in-frame stop remains inside the coding sequence. That is what makes the option safe to switch on globally, and it is pinned by a test.

    The level lives on the overlap, not on the call:

    readthrough: Readthrough = field(
    default=Readthrough.NONE,
    on_setattr=invalidates("_full_cds_alleles", "_full_peptide_alleles"),
)

    A parameterised cds_alleles(*, readthrough=…) was tried first and rejected: reference_cds and friends would keep answering at the default level while the fact layer asked for another, so one object would hold two disagreeing answers. As a field there is one cached value, every accessor agrees, and invalidates(...) makes reassignment recompute rather than serve a stale cache. AnnotatorContext.readthrough carries the run-scoped setting and prepare() stamps it onto each overlap before the sequence tier is reached — the same ordering rule the codon cache already depends on. Nothing in facts/sequence.py knows the option exists.

    Gotchas¶

    • Translation is bounded by end_bound, never by "the next stop codon anywhere". It stops at the first in-frame stop within the window, or at end_bound if there is none. By default it does not read into the 3'UTR looking for a replacement stop, and does not read past the transcript. A stop-losing edit therefore yields an alternate peptide with no * — a legitimate answer, not an error. That default can be lifted per run; see Opt-in readthrough above.
    • cds_stop_lost checks the reference's own stop position, not "is there a stop anywhere". A frameshift can leave a coincidental in-frame * elsewhere; treating that as the stop being retained is wrong. The facts compare alternate_peptide[reference_stop] specifically, and require the prefix up to that point to match.
    • An insertion exactly at cds_end0 is currently treated as inside the CDS (Case 2, 13 >= 13), the mirror of an insertion at cdna0 being treated as 5'UTR. For a well-formed CDS this is masked entirely — the window still ends with the reference's own stop codon, so _nucleotide_sequence_up_to_stop truncates there and the inserted bases never survive. It would only surface on a CDS with no terminal stop (cds_end_NF-style incomplete annotation).
    • delta must be computed from spliced-transcript offsets, not the genomic span. A deletion whose genomic span crosses an intron removes fewer transcript bases than its genomic length suggests; genomic_span_to_cds_offsets already accounts for this, which is why every offset here is transcript-wide rather than CDS-relative.
