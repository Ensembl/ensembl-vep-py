    Consequence annotators: developer guide¶

    How this codebase decides which Sequence Ontology (SO) consequence terms apply to a variant, and how to work on it without breaking anything.

    The idea in one paragraph¶

    Ensembl VEP decides consequences with ~76 Perl predicate functions, 44 of which call each other to suppress themselves (104 call sites). Adding one splice term there means auditing five neighbouring function bodies. Here the same logic is split three ways: facts (named, cost-tagged, memoised properties of one variant-against-one-feature), rules (each SO term as a boolean formula over fact atoms, plus a declarative subsumes list), and annotators (interchangeable strategies that evaluate the rules). Suppression is declared on the winning term instead of being scattered through predicate bodies, so adding a term touches one catalogue record.

       facts                rules                          annotators
   ─────                ─────                          ──────────
   overlap_cds   ──┐    stop_gained =                  linear          ─┐
   partial_codon ──┼──►   overlap_cds                  staged           │
   is_snv        ──┤      & !partial_codon             columnar         ├──► list[OverlapConsequence]
   peptide_...   ──┘      & alt_peptide_has_ter       columnar-staged  │
                          & !ref_peptide_has_ter                      ─┘
   what is true         which term follows             how to work it out

    The invariant that makes it safe: every annotator must produce byte-identical output. A new strategy is a candidate you diff against the incumbent, not a rewrite you have to trust.

    The two contexts¶

    They are split by lifetime, and that is the only thing that distinguishes them.

    • context/fact.py — FactContext is one (variant, feature) overlap. It holds the fact memo table, the cost counters, and the uncharged shared intermediates (variant_span, biotype) that more than one fact would otherwise recompute.
    • context/annotator.py — AnnotatorContext is one annotation run. It holds every cache whose unit of reuse is bigger than a single overlap: the zone map, the shared-codon cache, and the candidate caches.

    Sharing is opt-in and total. Construct one AnnotatorContext and pass it to every annotator that should share; pass nothing and each annotator gets a private, empty one. Whether caches are shared must never change the terms produced — that is what makes a cache safe to benchmark by turning it off, and it is asserted directly in tests/annotators/consequence/context/.

    context = AnnotatorContext(codon_cache=CodonEditLRUCache(), zone_map_cache=ZoneMapCache())
annotator = ColumnarStagedAnnotator(annotator_context=context)

    The annotators¶

    Every one produces identical terms. They differ only in how much work they avoid — and caches are orthogonal to the strategy, which is why there are five Python strategies rather than a cross-product of names.

    Name What it does cost/ctx ms/1k
    consequence.linear VEP-faithful: cheap-guard digest, candidate cache, rank-ordered scan. The conformance reference. 196.3 48.9
    consequence.columnar Bit-parallel over a batch. Cuts dispatch, not fact cost — note its cost/ctx ≈ linear's. 195.8 36.9
    consequence.staged Cheap facts first, then propagate requires implications; expensive tier only when a rule is still undecided. 74.8 29.9
    consequence.columnar-staged Columnar + requires propagation as bit-parallel forced-false masks. 73.9 19.5 (batch)
    consequence.columnar-kernels columnar-staged, with the cheap fact columns filled by native batch kernels. Only flat integer arrays cross FFI. 71.9 17.3 (batch)

    The zone map and the shared-codon cache are not strategies — they are caches any strategy can be built with, so they multiply this table rather than extending it:

    ColumnarStagedAnnotator(zone_map=ZoneMapCache(), codon_cache=CodonEditLRUCache())

    A note on the regular.* names in this document. The strategy namespace was regular. before annotators/regular/ became annotators/consequence/strategies/. Live strategies were renamed with it (regular.linear → consequence.linear); retired ones — regular.zonemap, regular.columnar-staged-zonemap, every regular.rust-* — are left spelled as they were actually registered, since renaming them would invent names that never existed.

    That combination is what used to be registered as regular.columnar-staged-zonemap; regular.zonemap was LinearFactsAnnotator(zone_map=ZoneMapCache()).

    Because the caches are orthogonal to the strategy, the benchmark measures the combinations explicitly rather than relying on registry names: vep bench matrix crosses every strategy with the cache sets given by --caches, each with fresh caches. Heavy-locus, batched:

    configuration cost/ctx ms/1k
    columnar-staged 73.9 19.5
    columnar-staged + zone map 17.4 10.2
    columnar-staged + zone map + codon cache 13.0 11.1
    columnar-kernels + zone map 16.4 8.1
    columnar-kernels + zone map + codon cache 12.0 9.0

    The codon cache lowers cost/ctx and raises wall-clock in both pairs — the clearest illustration in the table of why both numbers are reported.

    Numbers are heavy-locus corpus, --fuzz 4000 --repeats 3. cost/ctx is weighted fact computations; native annotators show 0.00 there because their facts are computed in Rust.

    Two results worth internalising:

    • columnar-staged's cost/ctx exactly equals staged's (74.84 both). That is empirical proof that the one-pass topological forced-false sweep is bit-identical to the per-context implied_false fixpoint it replaces.
    • A native zone map bought nothing (14.73 vs 15.58 ms/1k — noise). Native fact costs flatten, so there are no expensive tiers left to avoid. The Python-side wins do not all survive a port.

    Common tasks¶

    Add or remove an SO term¶

    uv run vep catalogue add --dry_run --term my_term \
    --accession SO:0001234 --impact MODERATE --so_parent SO:0001060 --when '"overlap_cds"'
uv run vep catalogue remove --term my_term --catalogue <path>

    It derives subsumes from SO parentage (if A is_a B, then A is more specific, so A subsumes B), cleans up dangling subsumes references on removal, renumbers ranks, and validates before writing.

    It will not invent a when formula. That is deliberate: a plausible-looking wrong rule passes conformance — every annotator agrees on the same wrong answer — and only surfaces later as bad biology. The script suggests candidate fact atoms and makes you author the rule.

    Naming a fact: the relation vocabulary¶

    Positional facts name the relation between the variant's span and the thing it is tested against, using one of four prefixes. Pick the one that is literally true of the predicate body:

    Prefix Meaning
    within_ the variant lies entirely inside the feature
    contain_ the variant entirely contains the feature
    intersect_ partial overlap — each side has a non-overlapped part
    overlap_ any overlap at all (the union of the three above)

    So overlap_feature (any overlap with the overlapped feature), contain_feature (the variant swallows it whole), overlap_cds, overlap_exon, overlap_donor_site, and so on. The noun is the thing tested against, and feature — not transcript — is correct wherever the body only reads Feature.start/Feature.end, because those facts hold for a Motif or Regulatory feature just as they do for a Transcript.

    overlap_five_prime_utr and overlap_three_prime_utr used to be the exception (in_five_prime_utr/ in_three_prime_utr, not genuine overlap tests) but no longer are — see their docstrings in consequence/facts/position.py for what they used to compute, the model bug that made the old names honest, and why fixing both was a semantic change rather than a rename.

    Naming a non-boolean helper¶

    Not everything in consequence/facts/ is a boolean rule atom — a fact's body often needs a non-boolean intermediate (a footprint, a peptide pair, a set of nearby intron windows), and the question of whether that intermediate should be @fact-decorated (memoised, cost-tracked, underscore-prefixed) or a plain helper function is a different one from the vocabulary above. See the module docstring of consequence/facts/base.py for the four categories and the eligibility/promotion rule — that module is the source of truth; this section only points at it so the rule is not duplicated and cannot drift. Every plain helper (categories 3 and 4) lives in consequence/facts/helper.py, not next to the boolean facts that call it; visibility there is controlled by __all__ alone, not by a leading underscore.

    Add a fact¶

    Facts are grouped by what question they answer: kind.py (what kind of feature/variant this is), position.py (coordinate comparison), sequence.py (sequence/peptide content or length arithmetic). Register a new fact in whichever one matches, with a cost tier and, if it is genuinely gated on another fact, a requires declaration:

    @fact(CostTier.MAPPING, deps=("overlap_exon",), requires=("overlap_exon",))
def my_new_fact(fact_context): ...

    deps = must be computed first. requires = must be true first — that is the implication the staged strategies exploit to settle rules without computing anything.

    requires is enforced by the decorator, not by you. The body runs only when every required atom is already true, so do not open it with if not get_fact(ctx, "overlap_exon"): return False — that is dead code, and hand-writing the guard next to the declaration is exactly how the two used to drift. requires names are folded into deps automatically too, so declare each one once.

    When a term cannot be a boolean formula¶

    Some VEP predicates genuinely resist boolean expression (data-dependent loops, non-boolean intermediates). fact does not require the body to be a formula composed from other atoms — it takes an arbitrary compute function — so there is no separate mechanism for this case, just an ordinary fact:

    @fact(CostTier.BOUNDS)
def my_bespoke_check(fact_context):
    for exon in fact_context.transcript.spliced_exons:  # arbitrary control flow
        ...

    Reference it from when exactly like any other atom — a bare "my_bespoke_check", or {"all": ["my_bespoke_check", ...]} alongside other conjuncts. One hard rule: such a fact may read other facts (via get_fact) but must never call another fact's compute function directly — that cross-calling is the VEP coupling this design exists to remove; going through get_fact keeps memoisation, cost accounting, and subsumes/prune's "adding a term touches one record" property intact regardless of how opaque a body's internals are. Declare cost/deps/requires honestly, same as any fact — every strategy (staging, zone maps, cheap-guard) reasons from those, not from whether the body happens to look like a formula, so an opaque fact loses nothing by being opaque as long as it is priced and gated truthfully.

    An earlier revision had a dedicated predicate decorator and a {"predicate": "name"} JSON sugar form purely to flag this case as greppable; both were removed as unneeded machinery over what a plain fact reference already does.

    Add an annotator¶

    Subclass ConsequenceAnnotator[FactRuleSet], implement annotate_feature_overlap, decorate with @register_annotator("consequence.my_strategy"), and import it from consequence/strategies/__init__.py. Conformance and the benchmark auto-discover registered names — you get both for free.

    Call self.annotator_context.prepare(fact_context) once per overlap, before computing any fact, and your strategy supports both caches with no further work. Register a name only for a genuinely different evaluation strategy — if the difference is "with a cache attached", that is a constructor argument, not a strategy.

    Push a fact into a native batch kernel¶

    consequence.columnar-kernels is the second, deliberately different bet on Rust. Where the regular.rust-* annotators move the whole annotator native — and so have to mirror a NativeTranscript across the boundary and keep it in step with the model — the kernels in src/rust/annotators/ruleset/batch_kernels.rs take flat integer arrays and nothing else. They do not know what a transcript is, and "do these two closed intervals overlap" will never grow a field.

    To add one: write the kernel taking Vec<i64> and returning a packed little-endian bitmap, export it in lib.rs, and have your annotator's seed_columns marshal the arrays and hand back {fact_name: int.from_bytes(bitmap, "little")}.

    The one rule that decides whether it pays: only seed facts that nothing reads through get_fact from inside another fact's body. Seeding a column is nearly free; fanning results back into per-overlap memos costs ~750 ns/context and eats the entire win. See the measured breakdown below.

    Handle more than one feature class¶

    build_fact_ruleset() takes no feature kind: one rule set covers every class, with no per-class subset to select. A rule restricted to one class says so in its own formula, via the FREE class facts in consequence/facts/kind.py (is_transcript, is_motif, is_regulatory, is_structural) — e.g. {"all": ["is_regulatory", "overlap_feature"]}. FactRule.cheap_guard (rules/rulesets.py) picks up that conjunct automatically, so an interleaved stream of Transcript and Regulatory overlaps settles the wrong-class rules on a type check without a separate masking pass. See columnar.py's own comment on why this needs no per-rule feature-class masking.

    Debug why a term did or did not appear¶

    uv run vep corpus describe --kind default                 # what is in the corpus, and every selectable overlap
uv run vep explain --annotator consequence.staged --index 40
uv run vep explain --compare consequence.staged,consequence.linear --index 40
uv run vep explain --name ENST0001_cds3_del1 --graph svg --output_file derivation.html
uv run vep explain --variant chrSynthetic:3005:ACG>- --transcript ENST0001

    Shows each fact's origin (computed / prefilled by zone map / codon-cache hit / forced False by requires) and how often it was read, per-rule verdicts with the reason they were settled, the pruning chain, and the emitted terms. --compare diffs two annotators and reports the first divergence — the tool you want the day a conformance test fails. An overlap is selected by --name, by --index, or by --variant CHR:POS:REF>ALT (with - for an empty allele) plus --transcript when several features share it; vep corpus describe lists all three for every overlap, and explain --list is the short form of that listing. The SVG graph format writes a linked HTML document with emitted terms first, pruned terms next, and non-firing terms last. Each term keeps its Boolean expression: blue nodes evaluated true, red nodes evaluated false, and white nodes were not observed.

    Tracing is opt-in and costs nothing when off. The annotation path records only what a later pass cannot recover — per-fact read counts, and which cache served which fact — so get_fact pays one is not None check and nothing else; origins, costs, forced-False facts and rule verdicts are all derived afterwards by trace/reconstruct.py. tests/trace/test_conformance.py is the gate on that derivation matching the run it claims to explain.

    The native annotators never trace, by design — since all are byte-identical, debug with a Python twin and you get the same answer.

    See the corpus the tests run against¶

    uv run vep corpus save --kind both --corpus_dir /tmp/corpus     # corpus.fa, corpus.gff3, corpus.vcf, manifest.json
uv run vep corpus describe --kind heavy --format markdown

    save writes the synthetic corpus as the files a real run reads, in the conventions the GFF3/VCF transcript and variation readers expect, with the generator's variant name in the VCF ID column. Loading it back is not a corpus verb: it is --input_file corpus.vcf --gff corpus.gff3 --fasta corpus.fa on any command, which waits on the file-backed overlap source. Until then every file still round-trips through the existing parsers (tests/corpus/test_store.py). describe shows chromosomes, transcripts, variant classes, how many distinct transcripts a batch chunk touches, and the overlap listing.

    Summarise a run, or profile the facts¶

    uv run vep stats --input_file annotated.vcf --format html --output_file summary.html
uv run vep stats --profile --kind default --annotator consequence.staged --format text

    Two planes, kept as two types on purpose. The run summary (stats/summary.py, RunSummary) is term-level and cheap -- about a microsecond an overlap -- so run writes it by default alongside its output, and vep stats --input_file rebuilds the same summary from any annotated VCF, ours or another tool's: output/parser/vcf.py reads the CSQ/ANN layout out of the header and seeds each allele's consequences directly, so it needs no --gff/--fasta, and Variation.most_severe_consequence / .class_so_term answer with zero transcripts attached. The fact profile (trace/run.py, RunTrace) is fact-level and measurably slower, so it is opt-in behind --profile; it says what every fact cost a run, how often it was read, and what the caches and requires propagation saved. Both satisfy one Reportable Protocol (stats/report.py) and go through one renderer (render/report.py), so --format html|text|json never branches on which it was handed.

    The profile report names the cost table it used. --fact_cost_override rewrites every fact's declared cost process-wide and never restores it, so two profiles are only comparable when that line agrees.

    Gotchas¶

    • Bare cargo test aborts with SIGABRT. The debug test binary cannot resolve libpython3.10.dylib. Always prefix DYLD_FALLBACK_LIBRARY_PATH=/Users/snhossain/miniconda3/lib.
    • validate_consequence_ruleset.py now exits 0. It used to report feature_truncation as a dead rule: the prototype's inherited formula was contain_feature & decreases_length & !is_deletion, and decreases_length and is_deletion are the same formula, so it was mathematically unreachable. The contradictory conjunct has no counterpart in the Perl and is gone; the rule now carries is_structural instead, which is the declarative form of VEP's return 0 if $bvfoa->isa('...TranscriptVariationAllele'). A non-zero exit is now a real failure.
    • Conformance is the gate, not a nicety. Any new strategy must be byte-identical to consequence.linear on both corpora before its timings mean anything.
    • cost/ctx and ms/1k rank strategies differently on purpose. cost/ctx measures the strategy; ms/1k measures this Python process. They disagree, and that disagreement is the point.
    • The declared cost tiers are a model, not truth. Declared 0/1/5/20/60; measured Python is nearly flat, and native code inverts the order (a coordinate map costs ~4x a codon translate). They rank strategies correctly; do not treat them as absolute.
    • At a PyO3 boundary, what you return costs more than how often you cross. Batching alone bought 1.08x; switching the return payload from term strings to u16 indices bought 3.48x.
    • Skipping a rule because something suppresses it is not sound on its own. prune() drops a term whenever any hit term subsumes it — and a hit term that is itself dropped still contributes its own subsumes. So eliding a suppressed rule loses whatever that rule would have suppressed. Concretely: splice_donor_region_variant suppresses splice_region_variant; skip splice_region_variant and coding_transcript_variant wrongly survives. A rule may only be skipped when its own subsumes are already covered.

    Measured negative results¶

    Kept deliberately, so they are not rediscovered at cost.

    • A native zone map bought nothing (14.73 vs 15.58 ms/1k — noise). Native fact costs flatten, so there are no expensive tiers left to avoid.
    • Native optimisation machinery does not pay at all. regular.rust-naive — every rule evaluated one by one, no staging, no zone map, no bit-parallelism — matches the fully optimised regular.rust-columnar-staged-zonemap (4.177 vs 4.182 ms/1k batched). The ~10.8x native speedup is entirely the FFI boundary shape (batched calls returning u16 indices), not the strategy.
    • Subsumes-topological early skipping is a small net loss. StagedFactsAnnotator(early_subsumption_skip=True) measured 28.81 → 29.07 ms/1k (boundary+fuzz) and 30.66 → 31.30 (heavy-locus), skipping only 2–3% of rule evaluations. Staging has already settled most suppressed rules cheaply, and the soundness condition above makes the skip much narrower than it looks. Off by default; the code and its tests are kept for the soundness trap, not the speed.
    • The shared-codon cache is a small wall-clock loss in Python (35.71 → 36.73 ms/1k) despite a 91.6% hit rate — building the key costs more than the work it saves.
    • Porting scalar primitives to Rust is worthless; porting column kernels pays ~1.2x. Two separate findings from the same experiment:
    • genomic_overlap is 4.6% of the no-zone-map path and 0.0% with a zone map attached — the zone map already eliminates that whole family in pure Python, for free. There is nothing left for a native genomic_overlap to win.
    • At kernel granularity, PyO3 is slower than Python at the arithmetic itself: 48.5 µs vs 28.4 µs for six variant-shape facts over a 256-context chunk. Converting a Python list to Vec<i64> and back dominates completely; the comparisons are noise. A kernel only pays if it displaces dispatch, not arithmetic.
    • consequence.columnar-kernels nonetheless measures 1.15–1.24x over consequence.columnar-staged (17.3 vs 19.5 ms/1k batched), because seeding eight fact columns removes ~2,000 get_fact calls per chunk. It cuts facts/ctx from 23.9 to 15.9 — a third of all fact computations — for a 1.2x wall-clock win, which is the clearest statement anywhere in this repo that the cost is dispatch, not facts.
    • An earlier version that also prefilled every seeded fact into the per-overlap memos measured 1.01x — dead even. The per-context fan-out is ~750 ns/context against ~190 ns for the kernel call. Column-only seeding is the whole difference between the two results.
    • The same lesson applied to the zone map is worth more than the Rust was, and needs no Rust. The zone map used to prefill its 16 facts into each overlap's memo, after which a columnar annotator still called get_fact once per (fact, overlap) to read them back — ~800k calls on the heavy-locus corpus, all memo hits. ZoneMapCache.columns returns them as bit columns instead; only the five named in MEMO_FACT_NAMES (those some other fact's requires guard reads) still need to exist per overlap. 13.16 → 10.42 ms/1k, a 1.26x win in pure Python.
    • Profiling answers "should the zone-map bisect be batched in Rust?" with: not on its own. ZoneMap.lookup — the bisect plus mask OR — is 3.9% of the fastest configuration's runtime, so a free native version caps out there. The whole of ZoneMapCache.columns is 16.1%, and the bisect is a quarter of it; the rest is the per-context Python loop that decodes 16 bits, applies the flank suppression and recomputes the UTR pair. Porting that is the ~13% opportunity, and it is still flat-array-shaped (zone starts, masks, inverted triples, bounds, utr_test) so it would not rot. The catch is batching: chunks average 18 distinct transcripts per 256 overlaps on the heavy-locus corpus, so it needs CSR-style arrays or a stateful native handle holding the maps — per-transcript calls of ~14 contexts are far too small to amortise PyO3's list conversion.

    Direct Python-object access from Rust (measured)¶

    RustNaiveAnnotator.direct_transcript_access = True makes Rust read the Python Transcript attribute by attribute (annotate_batch_indices_direct in src/rust/annotators/consequence/strategies/naive.rs) instead of being handed a NativeTranscript built and cached on the Python side. It deletes the Python-side mirror — the hand-listed field extraction in annotators/rust/base.py that is the part of the native port most likely to fall behind the model.

    corpus mirror direct access
    boundary+fuzz (4 transcripts) 4.43 ms/1k (10.98x) 4.66 ms/1k (10.44x)
    heavy-locus (36 transcripts) 5.32 ms/1k (9.96x) 6.15 ms/1k (8.62x)

    It costs 5–16%, and you keep 8.6–10.4x. Much cheaper than it looks, because the adapter already groups a chunk by transcript, so extraction happens once per (chunk, transcript) group rather than per context — ~3.5k extractions instead of 36 on heavy-locus, not 50k.

    The spread between the corpora is the amortisation: the mirror is built once per transcript for the annotator's lifetime, so the more variants share a transcript the better it looks. heavy-locus has 1,404 variants per transcript and loses 16%; boundary+fuzz has ~870 across only 4 transcripts and loses 5%. A corpus with few variants per transcript would favour direct access outright.
