    Typing Conventions¶

    All code must use explicit type annotations for function signatures, class attributes, and variables where appropriate.

    Rules: - Use standard Python typing (PEP 484, PEP 604). - For return types that may be a value or None, use Type | None instead of Optional[Type]. This is more cleaner. Also type checking does not happen at runtime, so does not affect users using python < 3.10 unless we are using type introspection dynamically at runtime.

    • Example: 
      def get_feature() -> Feature | None:
    ...
      Instead of: 
      def get_feature() -> Optional[Feature]:
    ...
    • Use built-in types where possible (e.g., list, dict, str).
    • Always annotate arguments and return values in public class, functions etc. Exceptions can be tests and private functions.

    We will enforce these conventions through static analysis tools (e.g., mypy) as part of our CI pipeline to ensure consistency and catch type-related issues early in the development process.

    Logging Implementation¶

    All logging in this project should use Python's built-in logging module. The recommended setup is as follows:

    • logging.basicConfig has been used in ensembl.vep.common.setup_logging function to setup logging configuration. This function should be called at the entry point of the application to ensure consistent logging behavior across all modules.
    • Log messages is sent to a file named {output_file}_warnings.txt consistent with old Ensembl VEP.
    • The log format includes timestamp, log level, logger name, and message.
    • For timestamps (%Y-%m-%dT%H:%M:%S) ISO 8601 format is used.
    • Always use named loggers (logging.getLogger(__name__)) for module-level logging.

    Example setup in a module:

    import logging

logger = logging.getLogger(__name__)

def some_function():
    logger.info("This is an info message.")
    logger.warning("This is a warning message.")

    Open question: Should we have a backward compatible option to have same manner of message formatting as old VEP?

    Docstring Style¶

    All docstrings in this project must follow the Google Python Style Guide for docstrings.

    Rationale: - Google style docstrings provide clear, consistent documentation and improve readability. - The docstring will facilitate automated documentation generation using mkdocs.

    No docstring, no visibility in the public docs!

    Key points: - Use triple double quotes (""") for all docstrings. - Include sections for Args, Returns, Raises, and Examples as appropriate. - Document types for all parameters and return values. - Keep descriptions concise and informative.

    Writing Classes¶

    Class Naming¶

    Class names must use CapWords (e.g., MyClass), in line with widely accepted Python conventions and PEP 8 guidelines.

    We are deliberately not using the Base prefix. Classes are named to reflect the object they model, and extended (if need be) via inheritance using progressively specific names using meaningful prefixes rather than just Base — for example, Variation as the parent class and StructuralVariation as its subclass.

    Rationale: This is a matter of stylistic preference — both approaches offer the same extensibility.

    Class attributes¶

    Non-derived attributes¶

    Attributes that are not derived from other attributes are defined in the class body with type annotations. They are generally not lazy-loaded or cached and further categorised into core attributes and externally-set attributes.

    Core Attributes¶

    Core attributes are those that are set during object initialization and are essential to the object's identity. They are included in the __init__ method generated by attrs. They do not have default values.

    from ensembl.vep.common import UnsafeSetterMixin, invalidates
class MyClass(UnsafeSetterMixin):
    core_attr1: int = field(on_setattr=invalidates('derived_attr1'))
    core_attr2: str
    derived_attr1: int = field(init=False)

    def some_method(self):
        derived_attr1 = self.core_attr1 * 2

cls = MyClass(core_attr1=1, core_attr2="foo")
with cls.unsafe():
    cls.core_attr1 = 2
    Externally-set attributes¶

    These are similarly not derived and externally set like core attributes but they are not essential to be in the __init__ method. The class is not responsible for calculating these attributes, so it should not enforce immutability or caching.

    They should still be defined in the class body (with type annotations) to be compatible with slots=True and to ensure they are tracked properly.

    class MyClass():
    core_attr: int
    externally_set_attr: int = field(init=False)

cls = MyClass(core_attr=1)
cls.externally_set_attr = some_external_method()

    Derived Attributes¶

    Derived attributes are read-only properties derived from one or more attributes. They are lazy-loaded (not part of __init__) and can be cached (using functools.cached_property).

    Read-only enforcement is handled by the using a combination of a protected variable (prefixing name with _) and a public variable property with no setter. The public variable should be used for all access outside of the class definition, the protected variable is for internal use only. Because the public accessible variable has no setter, you should never assign directly to it, mypy will throw a misc error if you do (property is read-only). Reading or assigning to the protected variable directly outside of the class definition will result in a W202 error by pylint. Both will fail the CI checks and should be avoided. Ensure mypy and pylint are enabled in your IDE for linting annotations during development.

    Seeding a derived attribute at (or after) construction: sometimes a derived attribute genuinely needs an escape hatch -- the common case is normally computed, but a caller occasionally has an authoritative value and wants to supply it directly instead of it being derived. Do not make the derived property itself directly writable to solve this (see the note at the end of this subsection for why). Two options, in order of preference:

    • Feature.derived_attr_seeds (a constructor-only kwarg every Feature subclass inherits): pass {"attr_name": value} and it pre-populates that attribute's protected slot before anything else runs, so the property returns the seeded value instead of computing one -- indistinguishable from a normally-computed value from that point on, including being cleared by whatever invalidates() hooks would clear a computed one. 
      transcript = Transcript(..., derived_attr_seeds={"cds": my_authoritative_cds})
assert transcript.cds is my_authoritative_cds  # never ran the normal CDS derivation
    • Feature.seed_attrs(**seeds): the same mechanism, callable at any time rather than only at construction. Needed whenever the attribute you want to seed depends on another field that is itself init=False (so it can only be assigned after construction, e.g. Transcript.spliced_exons) -- seeding at construction time would just be invalidated the moment that field is assigned afterwards. 
      transcript.spliced_exons = [...]  # init=False -- must be set post-construction
transcript.seed_attrs(cds=my_authoritative_cds)  # now safe: nothing left to invalidate it

    For a one-off bespoke _override field instead of this generic mechanism (still a valid, slightly more explicit alternative -- see Translation.exon_coding_end_override), see the pattern below for how to keep the override and the normal derivation composed safely, and note the more advanced case: if a derived attribute needs to check whether a different derived attribute was itself already seeded or computed (not just its own core-attribute inputs), reading that sibling through its normal public property is unsafe if the two can derive from each other -- ordinary attribute access (including getattr(obj, name, default)) still triggers computation on a miss, default or not. Use ensembl.vep.common.is_resolved(instance, "_sibling_name") instead: it checks whether the protected slot already has a value without ever computing one, by calling the slot descriptor's own __get__ directly rather than going through the class's normal (compute-on-miss) attribute lookup. See Transcript._locate_coding_boundary (models/genic/transcript.py) for a real case where this matters: exon_coding_start can derive from a seeded cds, and cds can derive from exon_coding_start -- is_resolved is what lets each direction check "did the other side already get an answer from somewhere else" without ever triggering the recursive case.

    Lazy-loading is achieved by setting init=False for the derived attribute, which means it will not be included in the __init__ method and will only be computed when accessed.

    Caching is implemented using functools.cached_property on the private variable, which stores the computed value after the first access and returns the cached value on subsequent accesses. In some cases, the derived attribute may not be cached, - if the computation is cheap and does not justify the overhead of caching, or - if the derived attribute is set by product of some internal computation and does not have its own function to be decorated with @cached_property.

    class MyClass(CachedAttributeGuardMixin):
    core_attr1: int
    _derived_attr3: int = field(init=False, default=0)    # default value for non-cached derived attribute that is set by internal computation

    @property
    def derived_attr1(self) -> int:
        return self._derived_attr1

    @cached_property
    def _derived_attr1(self) -> int:
        # perform expensive computation here using core_attr1
        return sum(range(self.core_attr1 * 2))

    @property
    def derived_attr2(self) -> int:
        # perform cheap computation here using core_attr1
        # does not justify caching
        return self.core_attr1 + 1

    @property
    def derived_attr3(self) -> int:
        # this attribute is set by some internal computation
        return self._derived_attr3

    @cached_property
    def _derived_attr3(self) -> int:
        # alternative to defining default value at attribute definition
        # can be used for some minor compuations for initial value assignment
        return 0

    def some_internal_computation(self):
        # perform some internal computation here and set derived_attr3
        # cannot do caching
        self._derived_attr3 = self.core_attr1 * 2
    Cache invalidation¶

    It is expected that core attributes are not changed after initialization. In the unlikely event they do need to be updated, the related derived attributes needs to be invalidated. Some derived attribute may also depend on other derived attributes, we may need to invalidate those as well.

    INVALIDATING USING A ATTRIBUTE WHOSE init=False is PROBLAMETIC; as it is not part of constructor when it is assigned and between object creation we might have some seeded value for the derived attribute.

    Invalidating cache dependent on core attributes: This is handled by using the invalidates hook with on_setattr. This has speed penalty for object creation and assignment of core attributes. Core attributes are not expected to be updated that much. 

    class MyClass:
    core_attr1: int = field(on_setattr=invalidates('_derived_attr1'))

    @property
    def derived_attr1(self) -> int:
        return self._derived_attr1

    @cached_property
    def _derived_attr1(self) -> int:
        # perform expensive computation here using core_attr1
        return sum(range(self.core_attr1 * 2))

    Invalidating cache dependent on derived attributes: Derived attributes may not be defined in the attribute list, so we cannot use invalidates hook. Instead, we can directly call invalidate function from the function that calculates the derived attribute that the other derived attribute depends on.

    class MyClass():
    core_attr1: int

    @property
    def derived_attr1(self) -> int:
        return self._derived_attr1

    @cached_property
    def _derived_attr1(self) -> int:
        invalidate(self, '_derived_attr2')  # invalidate dependent derived attribute

        # perform expensive computation here using core_attr1
        return sum(range(self.core_attr1 * 2))

    @property
    def derived_attr2(self) -> int:
        return self._derived_attr2

    @cached_property
    def _derived_attr2(self) -> int:
        # perform expensive computation here using derived_attr1
        return self.derived_attr1 + 1

    Resetting derived attribute which does not have its own function: In some cases, the derived attribute is set by some internal computation and does not have its own function to be decorated with @cached_property (third case mentioned in Derived Attributes). So, if we invalidate the attribute and in some place we try to access it, we will run into error. In such cases, we can use reset_attrs that will instead of invalidating the attribute, reset it to its default state.

    Note: In some cases, we may want to allow updating core attributes without invalidating derived attributes. In that case, we can also use the UnsafeSetterMixin mixin. It allows using context managers to temporarily disable cache invalidation for faster but unsafe attribute update. Generally this should not be necessary. ```python class MyClass(UnsafeSetterMixin): core_attr1: int = field(on_setattr=invalidates('_derived_attr1'))

    @property
def derived_attr1(self) -> int:
    return self._derived_attr1

@cached_property
def _derived_attr1(self) -> int:
    # perform expensive computation here using core_attr1
    return sum(range(self.core_attr1 * 2))

    cls = MyClass(core_attr1=1) with cls.unsafe(): cls.core_attr1 = 2 # does not invalidate derived_attr1 

    ### Use of attrs

We heavily use the `attrs` module for writing classes. All classes use the following `attrs` decorator defaults:

**`slots = True`**

Slotted classes are enabled by default for improved memory efficiency and attribute access performance.

**Caveat:** Slotted classes come with known limitations. Refer to the [attrs glossary on slotted classes](https://www.attrs.org/en/stable/glossary.html#term-slotted-classes) for a full list.

**Rationale:** This is an intentional design constraint. Requiring all attributes to be declared upfront — including private or cache-related ones — prevents hidden state from accumulating across the codebase. Readers should be able to understand an object's full structure without hunting through unrelated code paths.

**`auto_attribs = True`**

All attributes must have explicit type annotations. This is enforced to maintain consistency and enable static analysis.

**`kw_only = True`**

All constructor arguments are keyword-only. This improves readability at call sites by making argument names self-documenting.

```python
# Good — intent is clear
MyClass(name="foo", value=42)

# Avoided — positional args obscure intent
MyClass("foo", 42)

    on_setattr vs Custom __setattr__

    We use a custom __setattr__ rather than on_setattr because on_setattr does not trigger for attributes defined via @cached_property — even at the class level. Since we want these cached attributes to be immutable and they cannot be registered in the attrs attribute list, a custom __setattr__ is necessary to enforce that constraint uniformly.

    Caveat: This approach may cause performance issues. As setattr is called for every attribute assignment, it can introduce overhead, especially if there are many attributes or frequent updates. This is a trade-off between enforcing immutability and performance.

    We can possibly emulate the attrs-generated __setattr__ if required in future - 

    def __setattr__(self, name, val):
    try:
        a, hook = sa_attrs[name]
    except KeyError:
        nval = val
    else:
        nval = hook(self, a, val)

    _OBJ_SETATTR(self, name, nval)
    This uses a dictionary lookup (sa_attrs) to resolve any validation or conversion hooks, falling back to a plain assignment if the attribute is not registered.

    Open questions: - Can __setattr__ be further optimised and eliminate loops and conditionals? - Is there a way to register @cached_property attributes in the attrs attribute list so that they are handled by on_setattr? - Is it better to implement custom caching logic with immutability instead of setattr?

    Multiple Inheritance¶

    Inheritance and Mixins¶

    Since we use slots=True, multiple inheritance is not straightforward — attrs requires that only one of the parent classes can use slots=True. And, if you inherit from class that is not using slots then you lose some of the benefits of slots in the child class especially slot inheritance.

    By design, we avoid multiple inheritance and prefer association when shared behaviour is needed.

    Rationale: Multiple inheritance is complex and easy to mess up (the infamous deadly diamond of death). You have to be careful with method resolution order (MRO) so that the correct derived methods are called. Then also you have to use super() consistently or never at all.

    When shared behaviour cannot be achieved through association, Mixins are the sanctioned exception. A Mixin is a lightweight class that provides a specific set of reusable methods without carrying state. Because they do not use @define or @attrs, they are compatible with slots=True classes and are never meant to be instantiated directly.

    Mixins must be defined with empty __slots__ to ensure they do not introduce a __dict__ that would break slot inheritance.

    # Correct: Mixin defined with empty slots
class SerialisableMixin:
    __slots__ = ()

    def to_dict(self):
        ...

    Lazy Loading and Caching¶

    For attributes that are not core attributes, we lazy_load them by setting init=False. Furthermore functools.cached_property is used to cache attributes after first access.

    The @cached_property is by default not suitable for use with slotted classes because it relies on the presence of a __dict__ to store cached values. However, as of attrs >= 24.1.0, cached_property is supported on slotted classes. See also: how cached properties work on slotted classes.

    Warning: cached_property is not thread-safe by default. If the class may be accessed concurrently, we use a threading lock to guard the property computation. Example: 

    from threading import RLock
from attrs import field
from functools import cached_property

class MyClass:
    _lock: RLock = field(factory=RLock, init=False)

    @cached_property
    def expensive_computation(self):
        with self._lock:
            # perform expensive computation here
            ...

    Note: The use of RLock instead of Lock to prevent deadlocks when trying to access a cached property from a another cached property.

    Position in a Sequence Region¶

    Coordinate Systems and Slices¶

    We use coordinate systems and slices to represent biological sequences, following the conventions established by Ensembl.

    A coordinate system defines the reference frame for a biological sequence — for example, a chromosome, clone, or contig. Ensembl uses 1-based indexing, meaning the first base of a sequence is position 1. Coordinate systems themselves carry no concept of strandedness.

    A slice represents a defined region within a coordinate system. Slice coordinates are relative to the start of the underlying sequence region, and by convention the start of a slice is always less than or equal to its end, regardless of strandedness. Strandedness is introduced at the slice level — the strand of a slice represents its orientation relative to the default orientation of the sequence region (which should always be forward).

    Features positioned on a slice have coordinates and strand values expressed relative to that slice. To obtain a feature's absolute position on the underlying sequence region, the seq_region_start, seq_region_end, and seq_region_strand methods should be used instead.

    Note: The concept of a "sequence region" is referenced in various parts of the codebase but has no dedicated class. A slice spanning the full length of a biological sequence with positive strandedness can be considered a functional equivalent of a sequence region.

    Coordinate Conventions¶

    All positions on a slice or sequence feature use start and end coordinates, where the condition start <= end always holds true.

    Exception: 1. Insertion variants described in Ensembl's default format can have end = start - 1. 2. Circular slice on a bacterial or mitochondrial DNA can have end < start.

    We use 1-based inclusive (closed) coordinates for all positions. This means that the first base of a sequence is at position 1, and both start and end positions are included in the feature span.

    Insertion coordinates¶

    As convention in Ensembl, for insertion variants, the start and end coordinates are defined such that end = start - 1. This is because in 1-based inclusive coordinates, length is represented as end - start + 1. An insertion has a length of 0, furthermore the adjacent start and end coordinates clearly indicate the position of the insertion between two bases.

    This convention is also convenient for calculating pre and post sequence for shifting algorithm. Nonetheless, it can be a source of confusion and errors, so it is important to be aware of this special case when working with insertion variants.

    Removal of Reference Bases¶

    When Variation objects are created any anchor bases are removed and the coordinates adjusted accordingly. For example, a deletion represented in VCF as 1 10 CAT C becomes AT/- with start=11 and end=12. An insertion such as 1 10 G GAT becomes -/AT with start=11 and end=10. The same is true for symbolic alleles. e.g. This variant 1 100 G <DEL>, becomes -/<DEL> and start is updated to 101.

    Getting away with circular dependency¶

    The heavy use of subfolders to group similar objects means that, depending on the way we structure our modules, there could be circular dependencies during import. The main source of circular dependencies here comes from using __init__.py files to expose a package's public API.

    The circular import is avoided using the following approaches:

    When importing from same package¶

    When importing within the same package, always import directly from the concrete module rather than through a package's public API.

    Prefer: 

    from ensembl.vep.models.genic.transcript import Transcript
    Over: 
    from ensembl.vep.models.genic import Transcript

    We also prefer absolute imports over relative imports, even within the same package: Prefer: 

    from ensembl.vep.models.genic.transcript import Transcript
    Over: 
    from .transcript import Transcript
    Absolute imports are more explicit, easier to trace, and consistent with PEP 8.

    Importing for type annotations¶

    When we are importing some module that is solely used for type annotations, typing.TYPE_CHECKING should be used - 

    if typing.TYPE_CHECKING:
    from some_module import some_function

    It allows importing the module only when type checking is performed (e.g. by static analysis tools), but not during runtime.

    Prevent direct circular import¶

    And, of course, we need to prevent direct circular imports (module A importing module B, and module B importing module A) by making sure we keep one-way dependency direction, i.e. the base class cannot inherit from any of the descendant classes.

    Containers¶

    We are using containers where we do not want to implement any behavior for an object, but useful to have a named and grouped representation of the data. They are defined using @frozen from attrs to create immutable data structures and available in ensembl.vep.common.(containers).
