ensembl.vep.annotators.consequence.rules package#

Boolean consequence rules over fact atoms.

The checked-in catalogue belongs here because only rule construction, validation, and editing consume it; the fact layer remains independent of catalogue metadata.

Submodules#

ensembl.vep.annotators.consequence.rules.catalogue module#

Load the checked-in overlap consequence catalogue (data/overlap_consequences.json).

The catalogue is the shared source of term, accession, rank, tier, impact, formula, subsumption, and ontology-parent metadata. when uses fact names and nested not, all, and any expressions. subsumes declares terms suppressed when both rules fire, while so_supported_parents records represented Sequence Ontology parents.

Fallback terms listed in EXCLUDED_TERMS intentionally have no when formula. All other applicability conditions, including feature-kind checks, remain explicit in catalogue formulas.

ensembl.vep.annotators.consequence.rules.editing.derive_subsumes(so_parent_accessions, entries_by_accession)[source]#

Walk so_supported_parents transitively to propose a subsumes set.

Direction: if the new term A is_a an existing catalogue term B (B is one of A’s SO parents), A is the more specific term, so A subsumes B – suppressing B whenever A also fires. Walking stays inside the catalogue: an SO parent accession not represented here cannot be proposed (there is nothing to subsume), and a present-but-when-less ancestor (an EXCLUDED_TERMS-style term, see consequence/rules/catalogue.py) is skipped from the proposal itself – it can never appear in a compiled FactRuleSet, so declaring a rule subsumes it would fail validation – but is still noted, and its own further-up parents are still walked past it.

Parameters:

  • so_parent_accessions (Sequence[str]) – The new term’s immediate SO parent accessions.

  • entries_by_accession (dict[str, dict[str, Any]]) – accession -> catalogue entry lookup.

Returns:

The proposed, sorted subsumes term tuple, and a list

of human-readable notes about the walk (skipped/unknown/excluded ancestors).

Return type:

tuple[tuple[str, ...], list[str]]

ensembl.vep.annotators.consequence.rules.rulesets.subsumes_topological_order(ruleset)[source]#

Order the rules so a rule comes after a rule that can suppress it.

After every rule has been evaluated, the subsumed terms are dropped. A rule whose term is certain to be suppressed by a higher-ranked term therefore evaluated for nothing. Evaluating in this order instead lets a scan skip such a rule outright.

The subsumes graph is acyclic. The RulePairFinding.contradictory_in and find_subsumption_cycles in rules/validation.py both reject cycles. So, a depth-first post-order is a valid topological sort. A cycle, were one ever introduced, it would not degrade to an infinite loop, and the conformance suite would catch the resulting output difference.

Parameters:

ruleset (FactRuleSet) – The rule set to order.

Returns:

Every rule in ruleset, ordered so that a rule appears after

every rule that (transitively) subsumes it.

Return type:

tuple[FactRule, ...]

ensembl.vep.annotators.consequence.rules.validation module#

Validate consequence rule structure and satisfiability.

Validation has three tiers:

  • StructuralChecks validates references, ranks, subsumption, and catalogue metadata.

  • RuleReachability and RulePairFinding search bounded FactAssignmentSpace instances.

  • Optional SolverChecks asks equivalent whole-rule-set questions through an SAT solver.

classmethod redundant_in(ruleset, *, max_union_support=18)[source]#

Find declared subsumes edges whose entailment is confirmed by the formulas themselves.

For each declared A subsumes B, check whether A.when logically entails B.when over every valid assignment of their combined support (i.e. whenever A’s formula could possibly be true, B’s formula is necessarily true too). Where it holds, the subsumption is logically redundant in the sense that A firing already guarantees B’s condition holds – the subsumes declaration is provably sound, not merely asserted. Where it does not hold under this bounded axiom set, that is not reported as an error: most of this catalogue’s subsumption edges rely on domain knowledge broader than the small declared axiom set here (e.g. “a deletion spanning the whole transcript necessarily also overlaps every intron and UTR” is true, but nothing in _EXCLUSIVITY_AXIOM_PAIRS encodes it), so a pair not appearing in this report is inconclusive, not suspect.

classmethod subsumes_so_parent_drift(ruleset)[source]#

Report where the declared subsumes graph disagrees with the SO so_supported_parents.

These are two genuinely different relations that happen to overlap a lot: subsumes is VEP’s empirical suppression behaviour (term A, if it fires, hides term B), while so_supported_parents is the Sequence Ontology’s is_a parent graph (term A is a kind of term B), restricted to parents also represented in this catalogue. A rule can subsume a term it is not an SO child of (e.g. suppressing a sibling), and a rule can have an SO parent it does not need to suppress (the parent’s own when may already be false whenever the child’s is true, with no pruning required). So this report is informational context for a catalogue reviewer, not a pass/fail check – drift here is common and often fine; it is a prompt to look, not a bug report.

Parameters:

ruleset (FactRuleSet) – The rule set to report drift for.

Returns:

One description per rule with at least one asymmetry between its subsumes

set and its SO-parent-derived term set, or an empty list if every rule’s two sets match exactly.

Return type:

list[str]

classmethod for_catalogue_entries(entries, baseline_entries)[source]#

Validate a candidate consequences list before it is ever written to disk.

Reuses ensembl.vep.annotators.consequence.rules.validation’s structural (Tier 1) and enumeration (Tier 2) checks over a FactRuleSet built from the candidate entries (see _ruleset_from_entries) – not the packaged catalogue, which is what makes this safe to call before a real term has been added or removed on disk. The two checks that hardcode a call to the packaged load_consequence_definitions() (report_missing_when_terms, report_subsumes_so_parent_drift) are intentionally not reused here, since they are defined in terms of the checked-in EXCLUDED_TERMS/catalogue rather than a candidate in-memory one; a needs-review, when-less addition is instead surfaced separately, at add-time, by resolve_when’s NEEDS REVIEW banner.

Unreachable-rule findings are diffed against baseline_entries (the catalogue before this add/remove was applied) rather than treated as build-breaking outright: the checked-in catalogue already carries one known, pre-existing dead rule (feature_truncation). Treating every unreachable rule as build-breaking here would permanently refuse every write against the real catalogue, for a reason unrelated to whatever term is being added or removed. A rule unreachable in both the baseline and the candidate is downgraded to an informational warning; one that only became unreachable in the candidate is a genuine regression introduced by this operation and stays build-breaking.

Parameters:

  • entries (list[dict[str, Any]]) – The candidate catalogue’s consequences list.

  • baseline_entries (list[dict[str, Any]]) – The catalogue’s consequences list before this operation, used only to distinguish pre-existing unreachable rules from new ones.

Returns:

errors/unreachable_rules non-empty means refuse to write; warnings are

informational only (see ValidationReport.has_errors).
