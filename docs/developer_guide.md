## Typing Conventions

All code must use explicit type annotations for function signatures, class attributes, and variables where appropriate.

**Rules:**
- Use standard Python typing (PEP 484, PEP 604).
- For return types that may be a value or None, use `Type | None` instead of `Optional[Type]`. This is more cleaner. Also type checking does not happen at runtime, so does not affect users using python < 3.10 unless we are using type introspection dynamically at runtime.

  - Example:
    ```python
    def get_feature() -> Feature | None:
        ...
    ```
    Instead of:
    ```python
    def get_feature() -> Optional[Feature]:
        ...
    ```
- Use built-in types where possible (e.g., `list`, `dict`, `str`).
- Always annotate arguments and return values in public class, functions etc. Exceptions can be tests and private functions.

We will enforce these conventions through static analysis tools (e.g., mypy) as part of our CI pipeline to ensure consistency and catch type-related issues early in the development process.

## Logging Implementation

All logging in this project should use Python's built-in `logging` module. The recommended setup is as follows:

- `logging.basicConfig` has been used in `ensembl.vep.common.setup_logging` function to setup logging configuration. This function should be called at the entry point of the application to ensure consistent logging behavior across all modules.
- Log messages is sent to a file named `{output_file}_warnings.txt` consistent with old Ensembl VEP.
- The log format includes timestamp, log level, logger name, and message.
- For timestamps (`%Y-%m-%dT%H:%M:%S`) ISO 8601 format is used.
- Always use named loggers (`logging.getLogger(__name__)`) for module-level logging.

Example setup in a module:

```python
import logging

logger = logging.getLogger(__name__)

def some_function():
    logger.info("This is an info message.")
    logger.warning("This is a warning message.")
```

## Docstring Style

All docstrings in this project must follow the [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings) for docstrings.

**Rationale:**
- Google style docstrings provide clear, consistent documentation and improve readability.
- The docstring will facilitate automated documentation generation using mkdocs. 

> No docstring, no visibility in the public docs!

**Key points:**
- Use triple double quotes (`"""`) for all docstrings.
- Include sections for Args, Returns, Raises, and Examples as appropriate.
- Document types for all parameters and return values.
- Keep descriptions concise and informative.

## Writing Classes

### Class Naming
Class names must use `CapWords` (e.g., `MyClass`), in line with widely accepted Python conventions and PEP 8 guidelines.

We are deliberately not using the `Base` prefix. Classes are named to reflect the object they model, and extended (if need be) via inheritance using progressively specific names using meaningful prefixes rather than just `Base` — for example, `Variation` as the parent class and `StructuralVariation` as its subclass.

**Rationale:** This is a matter of stylistic preference — both approaches offer the same extensibility.


### Class attributes

#### Core Attributes
Core attributes are those that are set during object initialization and are essential to the object's identity. They are defined in the class body with type annotations and are included in the `__init__` method generated by `attrs`.

Core attributes are not lazy-loaded or cached. Instead, they are used to generate derived attributes that are lazy-loaded and in some occassion cached.

It is expected that core attributes are not changed after initialization. In the unlikely event they do need to be updated, the related derived attributes needs to be invalidated. This can be automatically handled by using the `invalidates` hook with `on_setattr`. This has speed penalty for object creation and assignment of core attributes. Core attributes are not expected to be updated that much.

In some cases, we may want to allow updating core attributes without invalidating derived attributes. In that case, we can also use the `UnsafeSetterMixin` mixin. It allows using context managers to temporarily disable cache invalidation for faster but unsafe attribute update. Generally this should not be necessary.

```python
from ensembl.vep.common import UnsafeSetterMixin, invalidates
class MyClass(UnsafeSetterMixin):
    core_attr1: int = field(on_setattr=invalidates('derived_attr1'))
    core_attr2: str
    derived_attr1: int = field(init=False)

    def some_method(self):
        derived_attr1 = self.core_attr1 * 2

cls = MyClass(core_attr1=1, core_attr2="foo")
with cls.unsafe():
    cls.core_attr1 = 2
```

#### Derived Attributes

Derived attributes are read-only properties derived from one or more core attributes. They are lazy-loaded (not part of `__init__`) and can be cached (using `functools.cached_property`).

**Read-only enforcement** is handled by the using a combination of name mangling with a private variable (prefixing name with `__`) and a public variable property with no setter. The name mangling makes it difficult to assign to the private variable directly from outside the class and prevents accidental overwriting. But it is ultimately upon the developer to not forcefully assign to the mangled attribute name (e.g. `instance._ClassName__derived_attr = value`).

**Lazy-loading** is achieved by setting `init=False` for the derived attribute, which means it will not be included in the `__init__` method and will only be computed when accessed.

**Caching** is implemented using `functools.cached_property` on the private variable, which stores the computed value after the first access and returns the cached value on subsequent accesses. In some cases, the derived attribute may not be cached,
  - if the computation is cheap and does not justify the overhead of caching, or
  - if the derived attribute is set by product of some internal computation and does not have its own function to be decorated with `@cached_property`.

```python
class MyClass(CachedAttributeGuardMixin):
    core_attr1: int

    @property
    def derived_attr1(self) -> int:
        return self.__derived_attr1

    @functools.cached_property
    def __derived_attr1(self) -> int:
        # perform expensive computation here using core_attr1
        return sum(range(self.core_attr1 * 2))

    @property
    def derived_attr2(self) -> int:
        # perform cheap computation here using core_attr1
        return self.core_attr1 + 1

    @property
    def derived_attr3(self) -> int:
        # this attribute is set by some internal computation
        return self.__derived_attr3

    @cached_property
    def __derived_attr3(self) -> int:
        # some default value
        return 0

    def some_internal_computation(self):
        # perform some internal computation here and set derived_attr3
        self.__derived_attr3 = self.core_attr1 * 2
```

#### Externally-set attributes
Some derived attributes are set by external code (e.g. attaching overlap feature to VariationAllele). The class is not responsible for calculating these attributes, so it should not enforce immutability or caching. 

However, they should still be defined in the class body (with type annotations) to be compatible with `slots=True` and to ensure they are tracked properly. They are also lazy-loaded.

```python
class MyClass():
    core_attr: int
    externally_set_attr: int = field(init=False)

cls = MyClass(core_attr=1)
cls.externally_set_attr = some_external_method()
```

### Use of attrs

We heavily use the `attrs` module for writing classes. All classes use the following `attrs` decorator defaults:

**`slots = True`**

Slotted classes are enabled by default for improved memory efficiency and attribute access performance.

**Caveat:** Slotted classes come with known limitations. Refer to the [attrs glossary on slotted classes](https://www.attrs.org/en/stable/glossary.html#term-slotted-classes) for a full list.

**Rationale:** This is an intentional design constraint. Requiring all attributes to be declared upfront — including private or cache-related ones — prevents hidden state from accumulating across the codebase. Readers should be able to understand an object's full structure without hunting through unrelated code paths.

**`auto_attribs = True`**

All attributes must have explicit type annotations. This is enforced to maintain consistency and enable static analysis.

**`kw_only = True`**

All constructor arguments are keyword-only. This improves readability at call sites by making argument names self-documenting.

```python
# Good — intent is clear
MyClass(name="foo", value=42)

# Avoided — positional args obscure intent
MyClass("foo", 42)
```

**`on_setattr` vs Custom `__setattr__`**

We use a custom `__setattr__` rather than `on_setattr` because `on_setattr` does not trigger for attributes defined via `@cached_property` — even at the class level. Since we want these cached attributes to be immutable and they cannot be registered in the `attrs` attribute list, a custom `__setattr__` is necessary to enforce that constraint uniformly.

**Caveat:** This approach may cause performance issues. As __setattr__ is called for every attribute assignment, it can introduce overhead, especially if there are many attributes or frequent updates. This is a trade-off between enforcing immutability and performance.

We can possibly emulate the `attrs`-generated `__setattr__` if required in future -
```python
def __setattr__(self, name, val):
    try:
        a, hook = sa_attrs[name]
    except KeyError:
        nval = val
    else:
        nval = hook(self, a, val)

    _OBJ_SETATTR(self, name, nval)
```
This uses a dictionary lookup (`sa_attrs`) to resolve any validation or conversion hooks, falling back to a plain assignment if the attribute is not registered.

### Multiple Inheritance

### Inheritance and Mixins

Since we use `slots=True`, multiple inheritance is not straightforward — `attrs` requires that only one of the parent classes can use `slots=True`. And, if you inherit from class that is not using slots then you lose some of the benefits of slots in the child class **especially slot inheritance**.

**By design, we avoid multiple inheritance and prefer association when shared behaviour is needed.**

**Rationale:** Multiple inheritance is complex and easy to mess up (the infamous deadly diamond of death). You have to be careful with method resolution order (MRO) so that the correct derived methods are called. Then also you have to use `super()` consistently or never at all.

When shared behaviour cannot be achieved through association, **Mixins** are the sanctioned exception. A Mixin is a lightweight class that provides a specific set of reusable methods without carrying state. Because they do not use `@define` or `@attrs`, they are compatible with `slots=True` classes and are never meant to be instantiated directly.

Mixins must be defined with empty `__slots__` to ensure they do not introduce a `__dict__` that would break slot inheritance.

```python
# Correct: Mixin defined with empty slots
class SerialisableMixin:
    __slots__ = ()

    def to_dict(self):
        ...
```


### Lazy Loading and Caching

For attributes that are not core attributes, we lazy_load them by setting `init=False`. Furthermore `functools.cached_property` is used to cache attributes after first access.

The `@cached_property` is by default not suitable for use with slotted classes because it relies on the presence of a `__dict__` to store cached values. However, as of `attrs >= 24.1.0`, `cached_property` is [supported on slotted classes](https://github.com/python-attrs/attrs/releases/tag/24.1.0). See also: [how cached properties work on slotted classes](https://www.attrs.org/en/23.2.0/how-does-it-work.html#cached-properties-on-slotted-classes).

**Warning:** `cached_property` is **not thread-safe** by default. If the class may be accessed concurrently, we use a threading lock to guard the property computation.
Example:
```python
from threading import RLock
from attrs import field
from functools import cached_property

class MyClass:
    _lock: RLock = field(factory=RLock, init=False)

    @cached_property
    def expensive_computation(self):
        with self._lock:
            # perform expensive computation here
            ...
```

Note the use of `RLock` instead of `Lock` to prevent deadlocks when trying to access a cached property from a another cached property.

## Position in a Sequence Region

### Coordinate Systems and Slices

We use coordinate systems and slices to represent biological sequences, following the conventions established by Ensembl.

A **coordinate system** defines the reference frame for a biological sequence — for example, a chromosome, clone, or contig. Ensembl uses **1-based indexing**, meaning the first base of a sequence is position 1. Coordinate systems themselves carry no concept of strandedness.

A **slice** represents a defined region within a coordinate system. Slice coordinates are relative to the start of the underlying sequence region, and by convention the start of a slice is always less than or equal to its end, regardless of strandedness. Strandedness is introduced at the slice level — the strand of a slice represents its orientation relative to the default orientation of the sequence region (which should always be forward).

Features positioned on a slice have coordinates and strand values expressed relative to that slice. To obtain a feature's absolute position on the underlying sequence region, the `seq_region_start`, `seq_region_end`, and `seq_region_strand` methods should be used instead.

> **Note:** The concept of a "sequence region" is referenced in various parts of the codebase but has no dedicated class. A slice spanning the full length of a biological sequence with positive strandedness can be considered a functional equivalent of a sequence region.

### Coordinate Conventions

All positions on a slice or sequence feature use `start` and `end` coordinates, where the condition `start <= end` always holds true.

**Exception:** 
1. An insertion variants described in Ensembl's default format can have `end = start - 1`.
2. Circular slice on a bacterial or mitochondrial DNA can have `end < start`.

We use **1-based inclusive** coordinates for all positions. This means that the first base of a sequence is at position 1, and both `start` and `end` positions are included in the feature span.


## Getting away with circular dependency

The heavy use of subfolders to group similar objects means that, depending on the way we structure our modules, there could be circular dependencies during import.

In some cases, it occurs becuase we are using type annotations to refer to classes that are defined in the same module or in a different module that also refers back to the first module. We can get around it by -
```
if typing.TYPE_CHECKING:
    from some_module import some_function
```
It allows importing the module only when type checking is performed (e.g. by static analysis tools), but not during runtime.

When we are actually instantiating the class that would cause circular import error. In that case, we can use local import instead of top-level import to delay the import until it is actually needed at runtime.

```python
class MyClass:
    def some_function():
        from some_module import SomeClass
        instance = SomeClass()
```

Another case is when we are using the class as base class for inferitance. In that case, we need to do global import. We need to make sure we keep one-way dependency direction, i.e. the base class cannot inherit from any of the descendant classes.
